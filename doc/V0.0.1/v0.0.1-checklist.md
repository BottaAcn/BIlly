  ```json
  "cds": {
    "requires": {
      "db": {
        "kind": "sqlite",
        "[production]": { "kind": "hana" }
      }
    }
  }
  ```
  **Attenzione a non mettere semplicemente `"db": "hana"` senza lo scoping per profilo**: risolve `hana` come DB anche per il profilo di sviluppo di default, il che farebbe puntare `cds watch` in locale verso HANA Cloud reale — che sappiamo già essere irraggiungibile da questa rete locale (vincolo di rete, spec §5). Verificato con `npx cds env requires.db --profile production` vs default: con lo scoping corretto, dev → sqlite, production → hana.
- **`app/index.html` non veniva incluso nel modulo `billy-srv` deployabile.** `cds build --production` genera solo i task `db` (hana) e `srv` (nodejs) — nessun task copia `app/` nel pacchetto quando non si usa l'HTML5 App Repository (scelta deliberata, vedi spec §3/§6). Scoperto ispezionando manualmente `gen/srv/` e il contenuto del `.mtar` prima del deploy (su richiesta esplicita dell'utente di controllare a fondo l'MTA). Se non corretto, la UI non sarebbe stata raggiungibile una volta deployato, nonostante tutto il resto funzionasse. **Fix**: aggiunto `billy-app/scripts/copy-app.js` (copia `app/` → `gen/srv/app` con `fs.cpSync`) e richiamato come secondo comando nell'hook `before-all` di `mta.yaml`. **Nota tecnica**: il primo tentativo di fix inlineava `node -e "...{ recursive: true }..."` direttamente nell'MTA YAML — falliva con `cannot unmarshal !!map into string` perché i due punti dentro l'oggetto JS (`recursive: true`) confondono il parser YAML in uno scalare non quotato. Risolto spostando la logica in un file `.js` dedicato, invocato senza caratteri speciali.
- **Verifica del nome tabella fisico (task 2.3):** l'output di `cds compile --to sql --dialect hana` e il vero artefatto HDI (`gen/db/src/gen/billy.Document.hdbtable`, ottenuto con `cds build --for hana`) mostrano entrambi `billy_Document` con identificatori **non quotati** e case misto (`title`, `embedding`, ecc.), non `BILLY_DOCUMENT` tutto maiuscolo come nel reference. Questo è comunque coerente con l'aspettativa originale: HANA esegue il case-folding degli identificatori non quotati in maiuscolo a livello di storage/query — quindi il nome effettivamente interrogabile via SQL resta `BILLY_DOCUMENT` con colonne `ID`, `TITLE`, `CONTENT`, `EMBEDDING`, `CREATEDAT`. **Confermato definitivamente in FASE 11**: la query `SELECT ... FROM "BILLY_DOCUMENT"` in `askBilly` ha funzionato al primo colpo contro HANA reale, nessuna correzione necessaria.
- **Auth `jwt` di default in produzione, anche senza `@requires` nel CDS.** Il primo deploy di `billy-srv` è crashato in loop con `Error: Authentication kind "jwt" configured, but no XSUAA instance bound`. Non basta lasciare `@(requires: ...)` commentato nel `.cds`: CAP in profilo produzione assume comunque `auth: jwt` di default. Va disattivato esplicitamente in `package.json`: `"cds": { "requires": { "auth": { "kind": "dummy" } } }`. Questa è la configurazione CAP corretta e standard per un servizio volutamente aperto (coerente con la richiesta esplicita dell'utente), confermata funzionante nei log post-fix (`"using auth strategy { kind: 'dummy' }"`).
- **Path REST reale: `/rest/billy/...`, non `/billy/...`.** CAP monta i servizi con `protocol: 'rest'` sotto un prefisso automatico `/rest/`, confermato dal log di avvio (`"serving BillyService { at: [ '/rest/billy' ], ... }"`). La UI (`app/index.html`) e ogni test manuale sono stati corretti di conseguenza. Non era documentato/assunto esplicitamente nella bozza originale — scoperto dal primo 404 in fase di test.
