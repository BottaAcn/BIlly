# Spec — Billy v0.0.1 (walking skeleton)

> Obiettivo di questo documento: definire **cosa** costruiamo in questa versione e **perché**, prima di scrivere codice. Il "come" passo-passo è nel documento gemello [v0.0.1-checklist.md](v0.0.1-checklist.md).

---

## 1. Scopo

Un **walking skeleton**: la fetta più sottile possibile che attraversa **tutti** i layer dell'architettura finale di Billy (CAP → HANA Cloud Vector Engine → SAP AI Core/Orchestration → risposta). Non è un prototipo throwaway: è la base reale su cui verrà costruito il progetto vero (modello dati, servizi, frontend definitivi verranno aggiunti sopra, non riscritti da zero).

**Domanda a cui questa versione deve rispondere, senza ambiguità:** *"Lo stack scelto (CAP Node.js + HANA Cloud REAL_VECTOR/COSINE_SIMILARITY + SAP AI SDK orchestration su Claude, con AI Core in un subaccount separato) funziona end-to-end, in questo landscape BTP, oggi?"*

Se sì → il resto del progetto è ingegneria nota, senza incognite tecniche. Se no → lo scopriamo in poche ore, non dopo settimane.

## 2. Cosa è IN scope

| # | Funzionalità | Perché serve a questa versione |
|---|---|---|
| 1 | Un'entità dati con colonna vettoriale reale su HANA Cloud (`Vector(3072)`) | Verifica che CAP genera DDL compatibile e che l'HDI accetta il tipo |
| 2 | Azione che genera un embedding via SAP AI SDK e lo salva in HANA | Verifica `AzureOpenAiEmbeddingClient` in scrittura reale |
| 3 | Azione che fa retrieval con `COSINE_SIMILARITY` via SQL nativo da CAP | Verifica il cuore del RAG |

| 5 | UI minima (2 form: aggiungi testo, fai domanda) | Serve solo a pilotare il test a mano, non è UX definitiva |
| 6 | Deploy reale su Cloud Foundry, bind a HDI container permanente | I test locali non possono validare HANA (vedi §5 vincoli) — serve la prova in ambiente reale |

## 3. Cosa è FUORI scope (deliberatamente)

| Escluso | Perché rimandato |
|---|---|
| Autenticazione reale (XSUAA attiva) | La struttura viene preparata (§2.7) ma resta spenta: l'app deve restare aperta a tutti per ora, su richiesta esplicita |
| Approuter, HTML5 App Repository, Work Zone | Servono solo quando il frontend reale (React) va in produzione — Fase 2 della roadmap in HANDOFF.md §6 |
| Upload file reali, Object Store, malware scanning | v0.0.1 lavora solo su testo incollato, non su documenti caricati |
| Modello dati completo (Asset, Chunk, Player, Season, PointEvent, certificationLevel) | Verrà introdotto quando si passa dal walking skeleton al progetto reale — vedi §7 |
| Chunking di documenti lunghi | 1 "documento" v0.0.1 = 1 embedding, senza split |
| Gamification | Non pertinente alla verifica tecnica |
| MTA **completo** (approuter + UI HTML5 + XSUAA attiva + html5-repo) | Questi moduli servono solo quando il frontend reale va in produzione — Fase 2 |

**Nota corretta rispetto a una prima bozza di questo documento:** l'MTA non è del tutto fuori scope. Il deploy dello schema su un HDI container **richiede** il meccanismo standard `mbt build` + `cf deploy` (è così che funziona il deployer HDI, anche nel reference SAP) — non è un `cf push` semplice. Quindi usiamo un **MTA minimo**: solo 2 moduli (servizio CAP + HDI deployer) e 1 risorsa (hdi-container). Niente approuter, niente UI come modulo separato, niente XSUAA bindata. Vedi §6 per il dettaglio.

## 4. Modello dati

Un'unica entità, nel namespace `billy`:

```cds
namespace billy;

entity Document {
  key ID      : UUID;
  title       : String;
  content     : LargeString;
  embedding   : Vector(3072);
  createdAt   : Timestamp @cds.on.insert: $now;
}
```

**Perché `Vector(3072)` e non un'altra dimensione:** misurato nella fase di pre-flight con `text-embedding-3-large` (vedi HANDOFF.md §4/§6.4) — non è un valore assunto, è stato osservato con un test reale.

**Nota tecnica da verificare in fase di esecuzione (checklist, task dedicato):** CDS genera il nome tabella fisico come `<NAMESPACE>_<ENTITY>` maiuscolo (es. nel reference SAP, `ai.db.Mails` → `AI_DB_MAILS`). Per noi ci si aspetta `BILLY_DOCUMENT`, ma va **confermato con `cds compile db/schema.cds --to sql --dialect hana`**, non assunto, perché serve per scrivere la query SQL raw di similarity.

## 5. Vincolo di rete noto (da NON dimenticare durante l'esecuzione)

Abbiamo verificato nella fase di pre-flight che **HANA Cloud rifiuta connessioni SQL dirette (porta 443, protocollo HANA nativo) da IP non-BTP**: il tentativo di connettersi da questa macchina locale con `@sap/hana-client` è fallito con "socket closed by peer" nonostante il TCP fosse raggiungibile. Le chiamate HTTPS verso AI Core invece **funzionano regolarmente in locale** (confermato dagli smoke test in `billy-smoketest/`).

**Conseguenza pratica per questa versione:**
- Sviluppo e test della **logica applicativa** (struttura del servizio CAP, chiamate embedding/LLM) → si può fare in locale con SQLite come DB di sviluppo
- Verifica **reale** di `Vector(3072)` + `COSINE_SIMILARITY` su HANA → possibile **solo dopo il deploy su Cloud Foundry**, dove l'app gira dentro la rete BTP

Questo non è un problema dell'architettura, è una caratteristica di sicurezza attesa per un'istanza enterprise. Va solo tenuto a mente per non perdere tempo a debuggare un "bug" che in realtà è questa restrizione nota.

**Incognita aperta da chiudere durante l'esecuzione (non assunta):** se `@cap-js/sqlite` (il DB usato in locale) supporti nativamente il tipo `Vector` e `COSINE_SIMILARITY` per permettere un test locale parziale. Se sì, bene, testiamo prima anche in locale. Se no, si salta direttamente al test post-deploy: non è bloccante in nessuno dei due casi.

## 6. Architettura tecnica di questa versione

```
[UI statica in app/, servita da CAP]
        |  HTTP (azioni REST — protocol: 'rest', non OData)
        v
[CAP Service — Node.js, JavaScript]
   |                              |
   | AzureOpenAiEmbeddingClient   | OrchestrationClient
   | (@sap-ai-sdk/foundation-     | (@sap-ai-sdk/orchestration)
   |  models)                     |
   v                              v
[SAP AI Core — subaccount        [SAP AI Core — stesso, via
 accenture-genai-finance-it]      orchestration deployment
   |                               d3e8489d36a60c9c]
   | credenziali via env var
   | AICORE_SERVICE_KEY (JSON)
   | — NON binding di servizio CF,
   | perché AI Core vive in un
   | subaccount diverso da CAP
   v
   (risposta embedding / completion)

[CAP Service] --SQL/HDI--> [HANA Cloud — subaccount
                             accenture-sapdiscover-italy-internal,
                             HDI container billy-hdi-container]
```

**Deviazione intenzionale rispetto al reference SAP (`btp-cap-genai-rag`):** nel sample SAP, AI Core vive nello stesso subaccount del CAP e viene bindato come service instance Cloud Foundry (vedi `mta.yaml` del reference, risorsa `generative-ai-hub`). Nel nostro caso questo **non è possibile**: AI Core è nel subaccount `accenture-genai-finance-it`, CAP sarà nel subaccount `accenture-sapdiscover-italy-internal` — un binding di servizio CF non attraversa subaccount diversi. Le credenziali AI Core vengono quindi passate come **variabile d'ambiente dell'applicazione** (`AICORE_SERVICE_KEY`, stesso pattern già validato negli smoke test), non come service binding.

**Meccanismo di deploy (MTA minimo):** a differenza di AI Core, l'HDI container **è** nello stesso subaccount di CAP, quindi si bind normalmente come servizio Cloud Foundry. Il deploy dello schema (`Vector(3072)` compreso) su HANA Cloud avviene tramite il meccanismo standard `@sap/hdi-deploy`, orchestrato da un **MTA minimo** con solo 2 moduli:

```
mta.yaml (billy-app, versione minima)
├── modulo: billy-srv        (type: nodejs)     — il servizio CAP, path ./gen/srv
├── modulo: billy-db-deployer (type: hdb)        — deploya lo schema, path ./gen/db
└── risorsa: billy-hdi-container (type: com.sap.xs.hdi-container)
```

Niente approuter, niente modulo UI separato (l'HTML minima viene servita direttamente dal modulo `billy-srv` da `app/`, una feature nativa di CAP), niente XSUAA bindata. Si costruisce con `mbt build`, si deploya con `cf deploy` — stesso comando del reference SAP, solo con meno moduli.

## 7. Definition of Done

La v0.0.1 è considerata **completa e verde** quando tutti questi punti sono veri, verificati (non assunti):

- [ ] L'app è deployata su Cloud Foundry (spazio `Team AI Contest 3`) via `mbt build` + `cf deploy` e risponde su una route pubblica
- [ ] Il modulo `billy-db-deployer` ha creato con successo la tabella con colonna `Vector(3072)` sull'HDI container `billy-hdi-container`
- [ ] Aggiungendo un testo dall'UI, l'embedding viene generato (chiamata reale ad AI Core) e salvato in HANA
- [ ] Facendo una domanda dall'UI, la query `COSINE_SIMILARITY` su HANA restituisce risultati con un ordinamento sensato (il documento più pertinente in cima)
- [ ] Claude Sonnet 4.6 risponde citando il contenuto recuperato (non risponde "a vuoto")
- [ ] Le risorse di test create in precedenza (HDI smoketest) sono già state ripulite — **confermato**, vedi HANDOFF.md §6.5
- [ ] `xs-security.json` esiste nel progetto con il pattern di ruoli Member/Admin, ma **non è bindato/attivo** — l'app resta accessibile senza login

## 8. Prossimo passo dopo questa versione

Se tutti i punti del §7 sono verdi: il rischio tecnico è chiuso. Si passa al modello dati reale (Asset, Chunk con `certificationLevel`, Player, Season, PointEvent — HANDOFF.md §2) costruendolo **sopra** questa base (stessa app, non un progetto nuovo), poi si aggiungono via via auth, frontend definitivo, upload file, gamification secondo la roadmap in HANDOFF.md §6.
